- Distinguish compilation, synthetic tests, queue admission, Telegram delivery/read state and actual system notification display. One does not prove the next. Keep `docs/development-status.md` current with actual results, skipped checks and remaining blockers.

## Common workspace and service boundaries

- Native SwiftUI/AppKit, macOS 26+, Apple Silicon. No Electron/Tauri product shell.
- Telegram is the first communication adapter, not the whole product. Integrate it and future mail/other channels into the common workspace with its service sidebar and shared contact dossier.
- Follow the selected references' verified layouts and workflows; do not invent a replacement interface. Use the service/reference map below. Confirm each changed screen against current reference source/screenshots and record remaining differences in `docs/reference-interface.md`.
- MainActor orchestrates UI state, approvals, commands and service-state aggregation. Each service owns protocol processing, persistence, Keychain, file/crypto preparation and media work on its own executors. Construct native background callbacks/pipelines without inherited MainActor isolation; publish results on main only after account/context/generation checks. Keep actor checks enabled and worker teardown asynchronous. Before changing these boundaries, read `docs/main-thread-boundaries.md` and `docs/architecture.md`.
- Contacts need the local PostgreSQL service, without communication accounts. Never read personal accounts, mail, system Contacts or messages without separate explicit authorization. Examples and UI QA use synthetic data and an isolated schema selected through `--database-config`.
- Development uses PostgreSQL and an adjacent S3-compatible service in Docker containers. PostgreSQL stores application records and attachment metadata/keys/receipts; archived attachment payloads belong in encrypted S3, never in PostgreSQL. Telegram's encrypted Postbox is a protocol cache, not a replacement for the application database. Before changing storage, read `docs/object-storage.md` and `docs/telegram.md`.
- Identity is (service, accountID, externalID). Imports, merges and undo must be atomic. Preserve manual overrides, source observations, identities and notes. Undo must stop after later edits; revision reuse must never enable stale undo.

## Telegram decisions

- Do not copy third-party code without exact license and dependency review. The Telegram engine uses the reviewed iOS revision selected from TelegramSwift, independently pinned in `Dependencies/TelegramEngine.lock.json`; build/run/test must never depend on `.references/` or a legacy project checkout. References are research inputs; explicitly authorized one-time migration is separate from product operation. See `docs/telegram.md` and `THIRD_PARTY_NOTICES.md`. Own code retains MIT; the combined app is GPLv3. Never copy the outer GPLv2-only UI or the reference application's embedded API credentials. Never enable engine logs containing private account data.
- Compile Makosh's own application API ID/hash into the binary from private build input or CI Secrets. The running app has no API JSON reader or API ID/hash input fields. Ordinary product builds fail closed without a valid pair; only an explicit source/test build may omit it and disable connection. Keep inputs/generated constants outside Git and logs. Only the application API pair is embedded: personal authorization, 2FA, session/Keychain keys and PostgreSQL/S3 credentials remain separate. Before changing connection/authentication or build configuration, read `docs/telegram.md`.
- Preserve existing session/cache/keys on startup or storage failure; missing keys fail closed. Do not reset a session to hide a crash, fabricate an initial sync cursor, silently log out or automatically resend an uncertain submission. Account authorization is entered by the user in the app.
- Retain every received message and its versions indefinitely in an independent append-only archive. Remote edits/deletion, cache eviction and disconnect must not delete retained history; add no TTL or automatic pruning. Acknowledge the durable source journal only after the archive commit. Content never received by this client cannot be recovered.
- Persist **Save files in S3** separately for each service/account/chat. Personal cloud chats default ON; groups and channels default OFF. Turning it OFF preserves message history and existing objects.
- S3 OFF forbids every new S3 copy, including outgoing preparation, normalized media, originals, covers and recovery/retry paths. Check policy before new admission; use the private encrypted local spool for preparation instead of database bytes. Enabling S3 later does not automatically promote local preparations. Preserve the documented in-flight/queued-work boundaries in `docs/object-storage.md`.
- Notifications have persistent per-account/per-chat show, preview and sound settings, available from the chat profile and the common settings screen. Keep global controls and Telegram server restrictions authoritative; one chat's rule must not affect another chat/account. Hide protected/secret content and respect OS screen-lock privacy.
- Check the ordinary bundle's macOS notification permission; a QA bundle's grant is not its grant. Request initial permission once for an eligible incoming event, revalidate policy/account after asynchronous consent, and retain explicit manual retry. Denial or an error must not cause repeated automatic prompts on each message.
- Active-window notification suppression requires the owning window to be key, visible and not minimized, as well as the app being active. `NSApp.isActive` alone is insufficient. Refresh on window changes and recheck after asynchronous callbacks; retain the user's configurable foreground setting.
- Local Makosh passcode and automatic app locking are excluded, not migration backlog. Switching devices during an active call is an accepted documented gap; selection before the next call remains supported. Reopen these exclusions only if the user changes scope. Telegram account 2FA and OS screen-lock privacy remain separate.

## Mail decisions

- Calendar integration and provider OAuth are explicitly outside the mail scope (user decision 2026-10-15). Do not count them as remaining migration work or add their UI. Manual TLS/STARTTLS accounts remain supported. Other agreed mail completion work continues independently of the paused real-account acceptance.
- Continue the existing `MakoshMail` / `MailWorkspaceModel` implementation; read `docs/mail-migration.md` and current status before changing it. MMail owns protocol/editor behavior; Aether owns verified layout/backdrop. Retain the independent `Dependencies/Mail.lock.json`, complete notices and verified TLS boundary. NIOSSL/BoringSSL products remain excluded from the linked GPLv3 app.
- Mail source changes (address, IMAP/SMTP host/port/security/user) require a new accountID; retained UID/notification/rule identity must never be rebound. Active SMTP/rule/schedule attempts hold a PostgreSQL session advisory lock across windows/processes; unknown resolution must reject a live owner and late completion must not overwrite a settled receipt.
- Mail identity includes account, exact wire mailbox, UIDVALIDITY and UID. Keep localized display titles separate from protocol paths. Load offline cache by folder/current generation with a stable paging cursor; old generations remain in the permanent archive.
- Preserve full text/HTML versions in append-only encrypted PostgreSQL. Raw RFC822/files belong in encrypted S3. The mail policy is per account/folder, default ON; OFF forbids all new S3 copies and uses encrypted local preparation for draft files. No remote deletion or MOVE may purge retained content. Never add automatic EXPUNGE.
- Persist SMTP and remote Drafts APPEND admission before dispatch; unknown results survive restart and prohibit replay until explicit resolution. Match late completions to a unique attempt as well as draft/content. Sent-copy failure never authorizes SMTP resend. Preserve every To/Cc/Bcc and attachment when reopening remote drafts; unchanged HTML must not be flattened on Save.
- Render mail HTML without JavaScript, remote resources or persistent web storage. Never invoke a network-capable HTML importer to populate the editor. Protocol/SQL/MIME/Keychain/crypto/file staging remain outside MainActor. Isolated native mail QA requires `qa_mail_` for both application/archive schemas; Telegram QA keeps its own prefix.
- Mail notifications follow MMail's new unread INBOX workflow; initial history and UIDVALIDITY changes establish a baseline. Persist encrypted checkpoints/preferences with page writes, consume events atomically, and never replay muted history. Global/account/folder/account-scoped sender rules restrict each other; foreground presentation defaults ON as in MMail. One application notification delegate and initial consent serve all channels, with separate opaque routes and callback-time privacy/account/read/window checks. Archive/Trash actions issue one existing worker MOVE after retaining the body, never EXPUNGE or automatic retry. Synthetic notification QA must not mark a real protocol connection as active.

## Telemost decisions

- Continue the existing `MakoshTelemost` first-stage service and common workspace. Before authorization, REST operations, catalogue/history, dossier or QA changes, read `docs/telemost-migration.md` and the approved `docs/superpowers/specs/2026-10-16-telemost-migration-design.md`; current evidence is in `docs/development-status.md`.
- The catalogue contains explicitly added/created meetings. Own OAuth registration, verified principal confirmation and account leases govern REST; HTTP401 keeps a durable reauthorization gate until a new confirmed grant. Unknown POST needs an explicit resolution; unknown PATCH needs exact-scope GET/review. Retain credentials, observations and attempts; mutation replay is always explicit.
- Participation uses a validated official HTTPS handoff. Native media/Linux WebRTC, chat, calendar, files and recording administration remain outside this first stage. Synthetic QA uses both `qa_telemost_` schemas and fake boundaries; native transport failure leaves visual acceptance unverified.

## Live QA and authorization

- Read the current QA scope/status in `docs/development-status.md` before using a real account. Use only the user-selected account and test peer; authorization for that test is not blanket access to other dialogs, account settings or sessions. Reading, messages/files, calls and microphone/camera use must stay within the actions authorized in the conversation; reuse existing authorization within that scope.
- A user pause/stop halts live UI/account/device checks. Stop only owned test processes as needed, preserve sessions/data and resume live checks only after the user's instruction. Independent static/unit/synthetic-service checks may continue. Keep the pause and outstanding real acceptance in the development ledger, not as a claim that Telegram is fully verified.
- Respect OS permission and tool boundaries. If a protected system dialog requires the user or a tool denies access, hand it off and report the concrete restriction; never bypass it, request passwords in chat or replace/reset the key to continue testing.
