# Резервная копия постоянного архива

Откройте Telegram → локальный архив (значок документа с замком) →
«Резервная копия…». Подключение к аккаунту Telegram не требуется. Нужны
настроенные локальные PostgreSQL, ключ архива в Связке ключей и, для сохранённых
вложений, доступное S3. В разработке сервисы запускает `scripts/dev-db.sh up`.

## Создание и проверка

1. Нажмите «Сохранить копию и отдельный ключ…». Выберите новое имя папки
   `.makoshbackup`, затем новое имя отдельного файла `.makoshkey` вне этой папки.
   Существующие назначения не заменяются. Используйте свою приватную папку;
   символические ссылки и доступные другим пользователям для записи родители
   не допускаются. Новые файлы имеют режим0600, папки0700, без наследуемых ACL.
2. Дождитесь сообщения об успешном создании. Переносите папку целиком.
   Файл ключа храните отдельно от копии. Потеря ключа делает копию недоступной;
   доступ к обоим файлам позволяет расшифровать историю и вложения.
3. «Проверить копию» проверяет все части истории, записи, метаданные и файлы,
   включая расшифровку и контрольные суммы. На экране видны количества/размеры,
   без текстов сообщений. Проверка возможна без PostgreSQL, S3 и Связки ключей.

Копия содержит только постоянный архив: исходные зашифрованные версии сообщений,
события удаления/исчезновения, квитанции, политики сохранения, ссылки и
зашифрованные объекты S3. Исходные номера последовательности и квитанции
сохраняются. PostgreSQL читается в согласованном MVCC-снимке только для чтения.
Сообщения, принятые после снимка, попадут в следующую копию. Незавершённые файлы
прерывают экспорт; дождитесь подтверждённого сохранения и повторите его.

Сеансы/авторизация Telegram, очередь отправки, кеш Telegram, контакты, данные
системы и API/S3/PostgreSQL-пароли в копию не входят. Зашифрованная история может
содержать ранее наблюдавшиеся секретные сообщения: постоянный архив сохраняет
их по тем же правилам, что и остальные уже полученные сообщения.

## Восстановление

1. Настройте PostgreSQL и S3 на компьютере назначения обычным способом.
   Выберите папку копии и отдельный ключ; выполните проверку.
2. Укажите новый идентификатор архива PostgreSQL: строчные латинские буквы,
   цифры и `_`, первый символ — буква, длина до63 байт. Любая уже существующая
   схема отклоняется, в том числе пустая или содержащая только контакты.
3. Подтвердите количество снимков/файлов и имя назначения. Полная проверка
   выполняется повторно; изменение копии после проверки требует новой проверки.
4. Дождитесь подтверждения и нажмите «Открыть восстановленный архив».
   Откроется существующее окно архива только для просмотра и выгрузки вложений.
   Эта операция не подключает аккаунты, не восстанавливает отправки и не
   переключает текущую запись сообщений.

Совпадающие объекты назначения проверяются полностью и используются повторно.
Отличающиеся данные/ключи не заменяются. Для отсутствующих объектов разрешена
новая копия только при включённом сохранении. Выключение в копии или текущем
рабочем архиве запрещает новые копии; даже если в старой копии было включено,
более строгое текущее выключение сохраняется в восстановленном архиве, включая
чаты без вложений. Поэтому для выключенного чата с отсутствующим объектом
понадобится исходное S3 с уже имеющимся файлом. Восстановление не включает
сохранение самостоятельно. Настройки проверяются повторно перед каждой записью
в S3; выключение в ходе операции останавливает её.

Ключ архива устанавливается в локальную Связку ключей без перезаписи. Тот же
существующий ключ используется повторно, другой ключ — конфликт. Исходный
архив и объекты не удаляются. Аутентифицированные добавочные соответствия
хранилищ позволяют читать исходные квитанции после переноса в другое S3;
старые версии Макоша без этой поддержки такие соответствия не понимают.

Для контролируемого выбора восстановленного архива при следующем запуске
существующая JSON-конфигурация базы поддерживает дополнительное поле
`archiveSchema`. Поле `schema` по-прежнему выбирает хранилище контактов;
`archiveSchema` выбирает только архив сообщений/файлов и по умолчанию равно
`schema`. Сохраните прежнее имя перед изменением, закройте приложение после
завершения принятой записи и измените только `archiveSchema`. Сначала сохраните
свежую копию рабочего архива. Если после восстановления менялись политики,
повторите восстановление в ещё одну новую схему при исходной конфигурации,
чтобы перенести текущие выключения; автоматического согласования при ручной
смене конфигурации нет. Самый безопасный обычный путь — отдельный просмотр,
оставляющий текущий архив рабочим. Контакты и авторизация не переключаются.

## Формат и границы

Формат v1 содержит аутентифицированный зашифрованный заголовок, части истории
и зашифрованные объекты. Отдельный криптографически случайный256-битный ключ
защищает заголовок/ключ архива; части используют отдельные производные ключи.
Контрольные суммы и аутентифицированные сведения связывают состав/количества
и размеры. Восстановление сначала создаёт приватный снимок входных файлов,
полностью проверяет его, затем допускает записи назначения. Неизвестная версия,
неверный ключ, повреждение, усечение, лишние/повторные элементы, некорректные
пути, символические ссылки и неполный состав отклоняются.

Копия v1 ограничена1млн строк,100тыс. объектов,64MiB удерживаемых метаданных,
1024 частями истории по32MiB и существующим лимитом4GiB на файл. Превышение
явно останавливает операцию без усечения. Это ограничения переносимого формата,
а не срок хранения: постоянный архив никогда автоматически не подрезается.

Папка копии публикуется атомарным переименованием без замены. Отдельный ключ
публикуется первым: поздняя ошибка может оставить неиспользованный файл ключа.
PostgreSQL и Связка ключей/S3 не имеют общей транзакции. До публикации схемы
проверяется весь состав; поздняя ошибка может оставить неиспользованный
совпадающий ключ или ранее разрешённые зашифрованные объекты S3. Исходные данные
не заменяются. При неопределённом результате COMMIT/связи сначала проверьте
назначение; не повторяйте операцию автоматически. Отмена ждёт фактического
результата: уже завершённое восстановление показывается как завершённое.

Изолированная QA использует синтетические ключи, отдельную схему
`qa_telegram_dossier_…` и локальный S3; личная Связка ключей не используется.
Результаты такой проверки не подтверждают работу с реальным аккаунтом Telegram.
