## Цель и принятые границы

Перенести следующий выбранный сервис в общий нативный Макош, сохранив боковую
панель сервисов, независимые исполнители, постоянную историю и досье.
Ранее принятый первый этап Телемоста: собственный SwiftUI-интерфейс встреч,
официальный REST для создания/настройки там, где доступен аккаунту, и участие
через официальный клиент/браузер. Linux/WebRTC остаётся отдельным вторым этапом.
Пауза живых проверок других сервисов сохраняется. Тестовый аккаунт Телемоста
не выбран; регистрация приложения и реальные операции не выполнялись.

Текущий `MeetingsView.swift` проверяет HTTPS-ссылку `telemost.yandex.ru` и
открывает её через NSWorkspace. Нет сервисного worker, аккаунтов, каталога,
постоянного хранения встреч или REST. Существующие Telegram/Mail/WhatsApp/Teams
сервисы продолжают работать; их код и данные не переносятся заново.

  на домене организации Яндекс 360 для бизнеса. Однако

  регистрация; отдельные права `telemost-api:conferences.read`, `.create`,

- [Создание](https://yandex.ru/dev/telemost/doc/ru/conferences/conference-create),
  [чтение](https://yandex.ru/dev/telemost/doc/ru/conferences/conference-read),
  [изменение](https://yandex.ru/dev/telemost/doc/ru/conferences/conference-update):

  `https://cloud-api.yandex.net/v1/telemost-api/conferences`.
- [Соорганизаторы](https://yandex.ru/dev/telemost/doc/ru/cohosts/cohosts-read):
  GET конкретной встречи с `offset`/`limit`. Это не список всех участников звонка.
- В просмотренном справочнике не подтверждён API списка всех встреч аккаунта,
  событий входящих звонков, сообщений чата, записей или завершения звонка.
  Каталог ниже содержит только созданные/добавленные в Макош встречи.
- [OAuth PKCE](https://yandex.ru/dev/id/doc/ru/codes/code-url) допускает S256
  и обмен кода без client secret при наличии verifier. Резервный
  [ввод кода](https://yandex.ru/dev/id/doc/ru/codes/screen-code) документирован.
  [User info](https://yandex.ru/dev/id/doc/ru/user-information) возвращает
  стабильные id/client_id даже без дополнительных прав на профиль.
- [Refresh](https://www.yandex.ru/dev/id/doc/ru/tokens/refresh-client) описывает

  истечение токена ведёт к явной повторной авторизации, без встроенного секрета,
  backend или предположений о безсекретном refresh.

## Варианты и рекомендация

1. **Рекомендуется: Swift-модуль официального API и native каталог встреч.**
   Завершает ранее принятый первый этап, соответствует service actors и не
   требует Linux runtime. Цена: собственный OAuth/REST/storage код и его тесты;
   медиа встречи остаются в официальном клиенте/браузере.
2. **Только улучшить открытие ссылок.** Минимальные затраты, но не реализует
   согласованные создание/настройку и историю встреч.
3. **Сразу портировать Linux signaling/media.** Требует отдельного доказательства
   протокола, зависимостей, macOS media/screen capture и реального аккаунта.
   Не включать в первый этап под видом готового переносимого движка.

## Результат первого этапа

- Несколько явно подключённых аккаунтов, вход/переподключение/отключение.
- Локальный каталог: созданные и добавленные по официальной ссылке встречи,
  поиск, избранное, локальные название/заметки, история изменений и экспорт.
- Создание обычной видеовстречи; чтение известных встреч; изменение комнаты
  ожидания `PUBLIC`/`ORGANIZATION`/`ADMINS` с явным действием пользователя.
- Постраничное чтение соорганизаторов. Страница/отказ не выдаются за полный
  список; исходные адреса сохраняются как наблюдения, а не доказанные личности.
- Копирование ссылки и открытие официального HTTPS URL через NSWorkspace.
  Успех открытия означает только передачу URL, не подключение к звонку.
- Явная связь встречи с выбранным досье, сохраняя источник и ручные сведения.

Создание трансляций, изменение соорганизаторов, настройки организации,
автоконспектирование, автоматическая запись и публичный чат не включаются
неявно. Поля, полученные от сервера, сохраняются и отображаются безопасно;
PATCH отправляет только явно изменённое поле комнаты ожидания. Локальный
заголовок не объявляется серверным названием обычной встречи.

Личные аккаунты остаются неподтверждённым сценарием. Календарь, реальные
входящие уведомления/звонки, переписка, собственные audio/video/screen sharing,
скачивание записей и файлов — вне этого первого этапа, а не реализованные
возможности. Пауза реальных проверок не отменяется этим документом.

## Архитектура и авторизация

Конкретный SwiftPM target `MakoshTelemost` использует Foundation, Security,
CryptoKit, AuthenticationServices и существующие Core/PostgreSQL facilities.
Новых внешних runtime библиотек не планируется. Независимый provenance manifest
фиксирует research SHA, просмотренные контракты и отсутствие runtime зависимости
от `.references/`; любое копирование требует точного license/notices review.

`TelemostWorker` владеет аккаунтом, запросами, операциями и отменой;
repository/vault actors — SQL, Keychain, crypto и сохранением. MainActor model
только принимает команды и публикует immutable snapshots с account/context/
generation guards после await. Конструкторы не начинают account IO. JSON parsing,
поиск/экспорт и закрытие ресурсов выполняются на сервисных исполнителях.

Собственный public ClientID и точный зарегистрированный redirect URI — явная
конфигурация интеграции. Вход через системную browser auth session с PKCE S256,
одноразовым state, ограниченным временем жизни и точной проверкой callback.
Если конкретная регистрация требует ручного кода, пользователь выбирает
документированный verification-code flow с отдельным verifier; тихого fallback
нет. Пароли Яндекса и client secret приложение не запрашивает.

После обмена кода worker проверяет user-info id/client_id по HTTPS, затем
показывает аккаунт перед привязкой. Reconnect того же accountID допускается
только с тем же principal/client; иной источник создаёт новый accountID.
Scopes по возможности: read базовый, create/update включаются отдельно.
Если сервер вернул урезанный scope, соответствующие действия недоступны;
401/403/402 показывают отдельные причины, а не общий статус «подключено».

Tokens хранятся в Keychain, не в JSON/URL/logs. Доступ API использует OAuth header;
endpoint/user-info host фиксированы, redirects с авторизацией запрещены.
Expiry/401 прекращает REST и предлагает явный повторный вход; история остаётся.
Refresh token не используется автоматически в этом этапе. Неизвестный исход
обмена кода не приводит к автоматическому повтору и не заменяет старый сеанс.
Отмена/отключение отзывает локальное выполнение; глобальный отзыв всех сеансов
и удаление сохранённого содержимого не производятся.

## Хранение и неизвестные результаты

Identity встречи: service `telemost`, неизменный accountID, точные байты
conference ID. Ссылки без API аккаунта имеют отдельную локальную область;
после подключения они не перепривязываются автоматически. Проверка URL
принимает только явно разрешённые официальные HTTPS hosts/path формата встречи;
credentials, нестандартный port, query/fragment, encoded separators и неоднозначные
ID отвергаются. `telemost.yandex.ru/j/{id}` — исходный поддерживаемый формат;
дополнительный официальный host включается только с отдельным проверенным правилом.

PostgreSQL хранит зашифрованные текущие records, append-only версии/наблюдения,
локальные поля, scope-bound preferences и durable attempts. Удаление ссылки из
текущего списка — локальное скрытие с сохранением архива. Remote404/403,
disconnect и переустановка connection не удаляют известные версии. Missing
Keychain key или failed COMMIT закрывают дальнейшие записи до явного исправления.

До POST/PATCH фиксируются immutable payload, operation/attempt ID и состояние
dispatching. Отдельный PG session advisory lock удерживается на время активной
операции, включая окна/процессы. После обрыва или недоказанного ответа состояние
unknown сохраняется через restart. POST не повторяется автоматически: неизвестно,
создана ли встреча. Явное разрешение позволяет привязать найденную официальную
ссылку к попытке после проверки известного ID либо признать исход неизвестным
и сознательно создать новую попытку с предупреждением о возможном дубликате.
PATCH unknown требует GET/review, без автоматического повторного изменения.
Поздний ответ сверяет точную попытку и не затирает уже разрешённый исход.

GET ограничены размером ответа/временем и retry budget, учитывают429/cooldown;
mutation/auth automatic retry отсутствует. Список соорганизаторов хранит
complete/incomplete и не теряет ранее наблюдённые страницы при частичном отказе.

В первом этапе нет получаемых file payloads: ссылки и параметры — records,
а не файлы. Не создавать фиктивный S3 toggle или скачивание записей. Будущий
перенос файлов обязан использовать encrypted S3, per-scope policy и запрет всех
новых копий при OFF; payload bytes никогда не попадут в PostgreSQL.

## Интерфейс и досье

Сохраняется существующий outer workspace/backdrop. Вместо disconnected-заглушки
в его средней колонке — account picker, поиск и список известных встреч;
справа — карточка выбранной встречи, ссылка, локальные сведения, доступ,
соорганизаторы, история и явные действия. Создание/редактирование в sheets.
Ошибки и pending/unknown состояния видны рядом с соответствующей операцией.
Референсные copy-link/browser действия воспроизводятся, fake таймер/микрофон/
камера/участники/состояние звонка не рисуются. Различия записываются в
`docs/reference-interface.md` с source locators и фактическими UI результатами.

Связь с существующим досье — явный выбор человека; meeting ID не становится
идентичностью этого человека, адрес соорганизатора не становится проверенным
user ID. В досье добавляется idempotent source-stamped note/reference через
ContactWorkspaceWorker, используя существующий ContactNote/SourceStamp и узкое
расширение команды. Заметки сохраняются существующим merge/undo. Она содержит
локально сохранённую ссылку/название и время наблюдения; не заявляет присутствие
человека на звонке. После await повторно проверяются окно, account, meeting и
досье. Ни один callback другого окна не переключает текущий выбор.

## Последовательность и критерии приёмки

Участки: контракт/identity/URL → OAuth/vault → PG/archive/attempts → REST/
reconciliation → native workspace/dossier → изолированная QA и итоговый обзор.
Подробный implementation plan составляется после утверждения этой спецификации.
Работа остаётся в текущем checkout, с hash baseline и отдельными checkpoints;
чужие dirty изменения, Git history и старые сервисы сохраняются.

Проверки: scripted OAuth/REST, real local PG, principal/scope isolation,
cancel/late callback, unknown restart/no replay, held-lock ownership, archive
retention, exact URL rejection, пагинация соорганизаторов, source-stamped note
dedup/merge/undo и native модели с управляемыми гонками. QA запускает только
Telemost fake endpoints/vault/browser handoff в fresh `qa_telemost_` application
и archive schemas, без других service hosts. Никаких настоящих встреч или
системных permission prompts до отдельного разрешения.

Обязательные финальные команды: `scripts/dev-db.sh up`, `scripts/test.sh`,
`scripts/build-app.sh`; проверка build без research clone; source/notices/diff
review; свежие XERJ fingerprints/queries. Native UI проверяется на synthetic
встречах и нескольких аккаунтах, при обычном/увеличенном масштабе, с честным
статусом симуляции. Перехваченный opener доказывает только handoff intent.

Готовность реализации не равна provider acceptance. Отдельно остаются собственная
OAuth регистрация, права/модерация Яндекса, business/personal eligibility,
реальные creation/info/update/cohosts, обычный Keychain, официальный клиент/
браузер, минимальная macOS и распространяемая сборка.

Rollback участков: прекращение Telemost worker/UI без удаления новых tables,
versions/attempts/keys; forward-compatible additive schema changes. Нельзя
откатывать весь checkout или сбрасывать базы других сервисов.
