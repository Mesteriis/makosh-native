# Раздел «Файлы» и Paperless — 2026-11-06

Статус: на утверждение пользователя. Кода нет. Проверен свежим читателем
(2 вопроса закрыты ниже). Первая из трёх частей
файлового направления, согласованного 2026-11-06 (порядок ниже).

## Зачем

У пользователя файлы разбросаны по каналам: вложения писем, документы из
Telegram и WhatsApp, файлы Teams. Все они уже попадают в один зашифрованный
архив Макоша (PostgreSQL `archive_file_events` + внутренний S3), но увидеть их
можно только из той переписки, где они пришли. Конкретная боль: приходит счёт
в почту — его нужно положить в Paperless-ngx (архив документов пользователя,
LXC 146, `https://doc.sh-inc.dev`, Paperless 3.0.5), сейчас это «сохранить на
диск → открыть Paperless → загрузить».

Этот проект даёт единое место для всех файлов и действие «Отправить в
Paperless» везде, где виден файл.

## Порядок частей (решение пользователя)

1. **Эта часть:** раздел «Файлы» с каталогом архива, подключение Paperless
   (просмотр и загрузка), «Отправить в Paperless» в контекстном меню файла.
2. Внешние хранилища SMB и S3 как источники и адресаты («Скопировать в…»,
   состояние «не в сети» без падений и зависаний).
3. Пересылка и ИИ: «Отправить в чат/письмо» из «Файлов», вложение из «Файлов»
   через «+» в составителях, карточка «файл» в панели ИИ с извлечением текста
   (PDF, txt/md/csv, Word/RTF, распознавание сканов). Документы Paperless,
   SMB и S3 попадают к ИИ только явной карточкой.

Части 2–3 здесь не проектируются; эта часть не должна им мешать: новые типы
хранилищ добавляются рядом с Paperless, а передача файла (см. `FileHandoff`)
переиспользуется для чатов, писем и карточек ИИ.

## Цели

1. **Раздел «Файлы»** в боковой панели сервисов (символ `folder`, между
   «Встречи» и «ИИ»). Боковая колонка: источники («Все файлы», «Почта»,
   «Telegram», «WhatsApp», «Teams») и блок «Хранилища» со списком подключений
   и кнопкой «+». Основная колонка: таблица файлов выбранного источника.
2. **Каталог архива.** Все файлы, сохранённые в архив Макоша любым каналом:
   имя, тип, размер, дата сообщения (при недоступности — дата сохранения),
   откуда (название чата / тема и отправитель письма / чат Teams), сервис.
   Поиск по имени, фильтр по типу (документы, изображения, видео, аудио,
   архивы, остальное), сортировка по дате (новые сверху) и имени.
3. **Действия над файлом** (контекстное меню строки и кнопки): «Посмотреть»
   (Quick Look), «Сохранить как…», «Открыть источник» (переход в чат;
   для письма — в раздел «Почта», как сейчас у карточки ИИ), «Отправить в
   Paperless…».
4. **Подключение Paperless.** Адрес, токен API (только Связка ключей),
   название; настройки по умолчанию для загрузки: тип документа и теги.
   Проверка подключения показывает версию и число документов. Несколько
   подключений допустимы.
5. **Архив Paperless в «Файлах».** Выбор подключения в блоке «Хранилища»
   показывает документы Paperless: поиск (полнотекстовый `query` Paperless),
   название, дата, тип, теги; постраничная подгрузка. Действия: «Посмотреть»
   (скачать во временную аренду и показать в Quick Look), «Сохранить как…»,
   «Открыть в Paperless» (браузер, страница документа).
6. **«Отправить в Paperless…»** во всех местах, где виден файл: плитка
   вложения письма, сообщение Telegram с документом/фото, сообщение WhatsApp с
   файлом, файл Teams, строка каталога. Открывается лист отправки: подключение
   (если их несколько), название (по умолчанию имя файла без расширения, до
   128 символов — предел Paperless), дата документа (по умолчанию дата письма/
   сообщения, можно очистить), тип документа и теги (по умолчанию из настроек
   подключения). После «Отправить» виден ход: «загружается» → «обрабатывается»
   → «Документ принят: #id» с кнопкой «Открыть в Paperless», либо причина
   отказа. Дубликат (Paperless отклоняет по контрольной сумме) показывается
   как «Такой документ уже есть в Paperless», не как ошибка.
7. **Устойчивость.** Сеть и чтение архива никогда не блокируют MainActor.
   Недоступный Paperless — строка подключения с пометкой и текстом ошибки,
   действия отвечают честной ошибкой; ничего не падает, не зависает и не
   повторяется автоматически.

## Не цели

- SMB, внешний S3, «Скопировать в…» — часть 2.
- Отправка файла в чат или письмо, вложение из «Файлов», карточки ИИ — часть 3.
- Изменение метаданных Paperless после загрузки, удаление документов в
  Paperless, удаление чего-либо в архиве Макоша (архив только добавляется).
- Автоматическая отправка в Paperless по правилам.
- Файлы, которые не были сохранены в архив (чаты с выключенным «Сохранять
  файлы в S3», старые письма без сохранённых вложений). Каталог показывает
  только то, что есть в архиве; «Отправить в Paperless» из самого письма при
  этом работает — вложение берётся тем же путём, что и «Сохранить».
- Локальные подготовки исходящих файлов при выключенном S3 (состояние `local`
  живёт только в спуле, в PostgreSQL его нет): остаются в архиве своего чата.
- Синхронизация или кэш документов Paperless на Mac: показ всегда живой.

## Анти-цели

- Документы Paperless не попадают ни в контекст ИИ, ни в индекс ИИ (часть 3
  даст это только явной карточкой).
- Токен Paperless не попадает в Git, логи, PostgreSQL, UserDefaults и тексты
  ошибок. В ошибках — код и короткое сообщение Paperless без токена.
- Никаких автоматических повторов отправки: неизвестный результат показывается
  как неизвестный; повтор — только рукой пользователя. Защита от задвоения на
  стороне Paperless (отказ по контрольной сумме) делает ручной повтор
  безопасным.
- Никакого собственного хранения копий файлов Paperless: временные копии для
  просмотра живут в аренде (каталог 0700, файл 0600) и удаляются при закрытии.
- Каталог не держит байты файлов — только метаданные в памяти.

## Ограничения

- Native SwiftUI/AppKit, macOS 26+, Swift 6 strict concurrency; MainActor только
  для состояния UI.
- Каталог читает `archive_file_events` через `MessageArchiveStore` (ключ архива
  из Связки ключей); байты — через `ArchiveFileRepository.export`. Таблицы
  PostgreSQL не меняются и остаются только дописываемыми; допускается один
  новый индекс (см. каталог).
- Paperless по HTTPS (`http` только для loopback — для тестов и локальных
  стендов), редиректы не выполняются, учётные данные в URL запрещены.
  Авторизация `Authorization: Token …`. Версия API запрашивается заголовком
  `Accept: application/json; version=N` с наибольшей известной Макошу версией;
  на `406` запрос повторяется без версии. Поля ответов читаются терпимо
  (`created` как дата или дата-время).
- Лимиты: загрузка в Paperless до 512 МиБ; каталог читает записи пачками по
  200 и отдаёт UI не чаще раза в секунду при первом заполнении.
- Изолированные QA-бандлы имеют свои UserDefaults и Связку ключей; синтетические
  проверки используют фальшивый сервер Paperless (URLProtocol) и тестовые
  схемы `qa_files_`.

## Как это устроено

### Модуль `MakoshFiles` (новая цель SwiftPM, зависит от `MakoshCore`)

- `FileCatalogueItem`: `recordID`, `identity` (service/account/conversation/
  message), `attachmentID`, `name`, `kind`, `byteCount`, `capturedAt`,
  `messageDate: Date?`, `sourceTitle: String?`, вычисляемая `category`
  (по расширению/`kind`).
- `FileCatalogue` (actor): читает `archive_file_events` в порядке `sequence`
  через новый метод `MessageArchiveStore.fileRecords(after: Int64, limit:)`
  (только `stored`; тот же путь расшифровки и проверок, что у `files(identity:)`),
  держит курсор и оставляет по одной записи на (identity, attachmentID) —
  самую позднюю. Исключает `rfc822-source` (копия письма целиком). Дата и
  автор берутся из `archive_events` того же сообщения новым методом
  `MessageArchiveStore.latestRecord(identity:)` — один запрос по
  `message_token` (`ORDER BY sequence DESC LIMIT 1`), для которого
  инициализация добавляет индекс `archive_message_sequence (message_token,
  sequence DESC)` по образцу двух существующих; таблицы и их строки не
  меняются, резервная копия индексы не содержит. Название источника — из
  `FileSourceResolving` (названия чатов/писем от сервисов; при неудаче —
  имя сервиса). Обновляется при открытии раздела и по кнопке «Обновить»;
  пока раздел открыт — каждые 30 с дочитывает новые записи.
- `FileHandoff`: `name`, `byteCount: Int64?`, `date: Date?`, `produce:
  @Sendable (URL) async throws -> Void` — единая передача файла из любого
  места (архивная запись, вложение письма через `exportAttachment`,
  загруженный медиафайл Telegram, аренда WhatsApp/Teams). Части 2–3 используют
  её же.
- `FileStorageConnection` (`.paperless(PaperlessConnection)`; часть 2 добавит
  `.smb`, `.s3`), `PaperlessConnection { id, name, baseURL, defaultDocumentType:
  Int?, defaultTags: [Int] }` с `validated()` по образцу `AIConnection`.
  `FileStorageRegistry` хранит список как JSON в UserDefaults
  (`makosh.files.storages.v1`); `FileStorageTokenVault` — токены в Связке
  ключей (`org.makosh.files.tokens.v1`, account = id подключения), по образцу
  `AITokenVault`.
- `PaperlessClient` (actor, URLSession без редиректов): `status()`
  (`GET /api/documents/?page_size=1` → число документов, `X-Version`),
  `tags()`, `documentTypes()`, `correspondents()` (постранично по `next`),
  `documents(query:page:)` (`ordering=-created`, `page_size=50`),
  `download(id:original:to:)`, `upload(_ handoffFile: URL, title:, created:,
  documentType:, tags:) -> taskID` (multipart `POST /api/documents/post_document/`),
  `task(id:)` (`GET /api/tasks/?task_id=`) → `.pending/.started/.success(documentID)/
  .failure(message)`. Ошибки: `PaperlessFailure.unauthorized/unreachable/
  rejected(status, reason)/duplicate(existingID?)`; дубликат распознаётся по
  тексту результата задачи.
- `PaperlessSubmission`: попытка отправки `{id, connectionID, fileName, title,
  taskID?, state: uploading/processing/accepted(documentID)/duplicate/
  failed(reason)/unknown, startedAt}`. Журнал — файл JSON 0600 в
  Application Support (`Makosh/PaperlessSubmissions.json`), чтобы «обрабатывается»
  и «неизвестно» пережили перезапуск; при старте незавершённые задачи
  дозапрашиваются по `taskID`. Опрос задачи: каждые 2 с до 3 мин, затем
  состояние остаётся «обрабатывается» с кнопкой «Проверить».
- `FilesWorkspaceModel` (MainActor, `MakoshFiles/Presentation`): выбранный
  источник, элементы каталога, поиск/фильтр/сортировка, подключения и их
  состояние, документы Paperless с постраничной подгрузкой, отправки.
  Каждое асинхронное обновление проверяет актуальность выбора (поколение).

## Решения, принятые за пользователя (проверить при чтении)

- Каталог исключает `rfc822-source` и показывает обложки видео/нормализованные
  фото как обычные файлы своего сообщения (одна строка на вложение).
- «Сохранить как…» и «Посмотреть» для Paperless берут **оригинал** документа
  (`?original=true`); архивный PDF Paperless можно открыть кнопкой «Открыть в
  Paperless».
- Дата документа по умолчанию — дата письма/сообщения; пользователь может её
  очистить, тогда Paperless определит дату сам.
- Подключения хранятся в UserDefaults (без секретов), токены — в Связке ключей;
  PostgreSQL для этого не используется.
- Опрос задачи Paperless ограничен 3 минутами, дальше — ручная проверка.
- Дата/автор файла читаются по `message_token` с новым индексом, а не
  перебором потока чата (иначе первое заполнение большого архива заняло бы
  минуты).
- Названия писем берутся из загруженных `mail.letters` по ключу письма;
  «Открыть источник» отключён для аккаунтов, которых в Макоше больше нет.
- Журнал отправок лежит рядом с другими данными бандла и у QA-бандлов свой.
- Пустой каталог при ещё не созданном архиве — пустой список, не ошибка.

## Ответы пользователя

- Периметр `https://doc.sh-inc.dev` (2026-11-06): к `/api/` Макош ходит по
  публичному имени **только с токеном** — без Basic-auth, allow-list и VPN.
  Сертификат публичный. Предел размера на nginx неизвестен: ответ `413`
  клиент показывает как отказ «сервер не принимает файл такого размера»,
  без повторов.

## Перед живой проверкой

- Токен API Paperless: его нужно создать в Paperless (профиль → API token) и
  ввести в Макоше. Прежняя настройка токена после удаления Authentik (LXC 141)
  не перепроверялась — перед живой проверкой убедиться, что токен работает
  (`GET /api/documents/?page_size=1` с заголовком `Authorization: Token …`).

## Что остаётся строителю

- Точные поля multipart и имена параметров Paperless 3.0.5; обработка
  `next` при постраничном чтении справочников.
- Разметка таблицы (`Table` против `List`), иконки по категориям, ширины
  колонок; формат дат.
- Правила категорий по расширению/MIME.
- Поведение при первом заполнении очень большого архива (прогресс в
  заголовке колонки).
