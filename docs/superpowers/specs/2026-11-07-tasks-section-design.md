# Раздел «Задачи»: локальный домен и Jira — 2026-11-07

Статус: на утверждение пользователя. Кода нет. Проверен свежим читателем
(6 вопросов, все закрыты моими решениями ниже). Первая часть направления
«Задачи»; вторая очередь перечислена в конце и в объём не входит.

## Зачем

Пользователь ведёт свои дела в одном месте и работает с задачами Jira
заказчиков: двигает их по workflow, списывает время, пишет комментарии,
передаёт коллегам. Сейчас это два мира: личные задачи вне Makosh, Jira в
браузере, время нигде не учитывается вместе. Конечная точка (пример —
проект MacTower пользователя): учтённое время превращается в счета и
оплаты. Эта часть кладёт основу: локальный домен задач по правилам
референса TaskOrchestrator, клиент Jira с пятью действиями и единый учёт
времени, на который позже лягут деньги.

Референсы (бизнес-логика, не интерфейс и не код):

- `yuriyda/TaskOrchestrator` `055c1f1` (MIT, Tauri + React + SQLite) —
  правила локального домена: статусы, приоритеты, зависимости и
  блокировка, повторы, undo, быстрый ввод строкой, журнал изменений.
- `mac-tower` `317eeaf` (MIT, репозиторий пользователя) —
  `MacTowerWorkTracking`: адаптеры Jira Cloud (почта + API-токен) и Data
  Center (PAT, OAuth 1.0a), транспорт, разбор ответов, переходы,
  worklog-синхронизация, таймер, сопоставление встреч с задачами по ключу.
  Решение пользователя: поступаем как с MMail для почты — протокольный слой
  переносится под собственным пином, деньги и счета не переносятся сейчас.

## Решения пользователя (2026-11-07)

- Два пространства внутри раздела: локальное и провайдера. Локальное живёт
  по правилам референса; у провайдера свой workflow, который не подменяется.
- Первый провайдер — Jira Cloud, вход по почте и API-токену. Data Center
  позже; граница для него закладывается сразу.
- В локальное пространство сами попадают задачи Jira, назначенные на
  пользователя, и задачи, где его упомянули в комментариях.
- Из Makosh в Jira нужны: переход по workflow, списание времени,
  комментарии, правка полей, смена исполнителя. Не полный движок Jira —
  клиент, дальше наша логика.
- Время: таймер по задаче и ручной ввод; время встречи (домен «Встречи»)
  должно списываться в задачу.

## Цели

1. **Локальный домен задач.** Задача: название, статус (`inbox`, `active`,
   `done`, `cancelled`), приоритет 1–4 (4 — без приоритета), список, теги,
   срок, дата начала, оценка, ссылка, счётчик переносов, зависимости от
   других задач, заметки, отметки создания, изменения, завершения и
   удаления. Правила — раздел «Правила домена».
2. **Быстрый ввод строкой.** Одно поле: `Название @список #тег !1 ^срок
   ~ключ` (`~` — зависимость по короткому коду задачи или ключу Jira).
   Разбор дат — правила референса, выписаны: `сегодня`/`завтра`/`вчера`
   (и английские); день недели (`пн`, `понедельник`, `mon`, `monday`) —
   ближайший такой день строго после сегодня; `+3d`, `+2w`, `+1m` — от
   сегодня; `20` — 20-е текущего месяца, если оно ещё впереди, иначе
   следующего; `20.04` и `20/04` — ближайшая будущая такая дата (в
   следующем году, если в этом уже прошла); `20.04.2026` — как есть;
   `5янв`, `янв5`, `5jan` — так же, как день и месяц. Токены без
   распознанной даты остаются в названии. Живой предпросмотр того, что
   получится.
3. **Jira как провайдер.** Подключения в Настройках → Задачи (название,
   адрес, почта, API-токен в Keychain, период опроса). Зеркалируются
   задачи `assignee = currentUser()` и задачи с упоминанием пользователя в
   комментариях. Каждая задача Jira в Makosh имеет идентичность (сервис
   `jira`, подключение, id задачи) и хранится как наблюдение провайдера с
   версиями; снятие назначения не удаляет ни наблюдения, ни локальный слой.
4. **Два пространства как две витрины одного хранилища.**
   «Мои» — локальные задачи и задачи Jira, назначенные на пользователя или
   с упоминанием, с локальным слоем (статус, приоритет, список, теги, срок,
   зависимости, заметки, время). «Jira» — задачи по подключениям, колонки
   по статусам workflow проекта (категории «К выполнению», «В работе»,
   «Готово» как группы), только те переходы, которые Jira разрешает для
   задачи. Одна задача видна в обеих витринах без дублирования записей.
5. **Пять действий в Jira**, каждое — явная отправка с журналом попыток:
   переход (с полями, которые переход требует), worklog, комментарий,
   правка полей (название, описание, приоритет, срок, метки), смена
   исполнителя (поиск по назначаемым пользователям проекта). Неизвестный
   результат никогда не повторяется сам. Описание правится только когда
   его ADF состоит из простых узлов (абзац, текст, перенос, упоминание,
   простые списки); иначе поле только для чтения с «Открыть в Jira» —
   форматирование чужой задачи не сплющивается, как и HTML письма.
   Поля перехода: поддерживаются текст, многострочный текст, число, дата,
   одиночный выбор и `resolution`; переход с другими обязательными полями
   показывает «заполняется только в Jira» и ссылку.
6. **Учёт времени.** Записи времени у любой задачи: источник `таймер`,
   `вручную`, `встреча`; дата, начало, длительность, примечание. Один
   идущий таймер на приложение, переживает перезапуск; остановка открывает
   черновик записи с правкой. У задачи Jira черновик по умолчанию
   предлагает отправить worklog (галочка снимается). Сводка за день и
   неделю по задачам в строке состояния раздела. Запись с подтверждённым
   worklog закрыта для правки длительности и даты и для удаления: меняется
   только примечание, исправление делается в Jira («Открыть в Jira»), а
   следующее чтение worklog задачи обновляет запись по `worklogID` или
   помечает её «удалён в Jira». Правка и удаление worklog из Makosh —
   вторая очередь.
7. **Время встречи.** В карточке встречи Telemost — «Списать время…»:
   черновик записи с выбором задачи (подставляется задача, чей ключ Jira
   найден в названии или заметках встречи — `localTitle` и `notes`
   записи каталога). «Открыть встречу» предлагает запустить таймер на эту
   задачу, если ключ найден; отказ ничего не запускает.
8. **Синтетическая проверка.** `--tasks-synthetic-preview` с
   `qa_tasks_` схемами и Jira в памяти (как Paperless у «Файлов»):
   зеркалирование, пять действий, таймер, черновики, витрины.

## Не цели

- Планер дня (слоты времени), повторяющиеся задачи, именованные цепочки
  (flow) с прогрессом, персоны референса, уведомления о новых назначениях
  и упоминаниях, карточка «задача» для ИИ, Data Center, деньги (ставки,
  счета, оплаты), синхронизация между устройствами — вторая очередь.
- Создание задач Jira из Makosh, вложения Jira, спринты, эпики и доски
  Jira Software, просмотр задач, не связанных с пользователем (поиск по
  JQL руками).
- Чтение чужих worklog: синхронизируются только worklog пользователя.
- Календарь: встреча Telemost в Makosh не имеет расписания, длительность
  берётся от пользователя (таймер или ручной ввод), не из календаря.

## Анти-цели

- Локальный слой никогда не пишется в Jira сам: смена локального статуса,
  приоритета, срока или списка не вызывает запросов к Jira. Единственный
  автоматизм в обратную сторону — задача, чей статус Jira перешёл в
  категорию «Готово», получает локальный `done`, если локальный статус ещё
  не `done`/`cancelled`.
- Никаких повторных отправок при неизвестном результате: worklog, переход,
  комментарий, правка и смена исполнителя с состоянием «неизвестно» ждут
  явного разрешения (перечитать задачу и сопоставить, либо отказаться).
  Двойное списание времени хуже пропущенного.
- Токен Jira, почта и JQL не попадают в логи, ошибки и вывод; сообщения об
  ошибках несут код и стадию, не тело ответа.
- Наблюдения провайдера и локальная история не удаляются при снятии
  назначения, удалении задачи в Jira или удалении подключения.
- Undo не воскрешает состояние, которого пользователь не видел: история
  короткая, в памяти, сбрасывается при применении внешних изменений.

## Ограничения

- Native SwiftUI/AppKit, macOS 26+, Swift 6, строгая изоляция. MainActor —
  модели витрин, команды, таймер как состояние; сеть, разбор, SQL, Keychain
  — в акторах сервиса.
- Jira Cloud REST v3 (список открыт, строитель добавляет то, что нужно
  для описанного): поиск `search/jql` с `nextPageToken`, `issue/{id}`
  с `expand=transitions`, `issue/{id}/comment`, `issue/{id}/worklog`,
  `issue/{id}/transitions?expand=transitions.fields`, `issue/{id}/assignee`,
  `user/assignable/search`, `myself`, `project/{key}/statuses` (колонки
  доски), `priority` (справочник для правки). Описание и комментарии — ADF; в Makosh хранится ADF как
  получен и текстовая проекция для показа и поиска; отправляются комментарии
  как ADF из простого текста (абзацы, упоминание как узел `mention` по
  accountId).
- Опрос: по умолчанию каждые 5 минут, запрос `updated >= -<окно>` по JQL
  зеркала, плюс обновление открытой задачи по требованию. Полный проход
  зеркала — при подключении и раз в сутки. Ограничения сервера
  (`Retry-After`, 429) соблюдаются, локальный backoff от 5 с до 1 ч, как в
  MacTower.
- Хранилище — PostgreSQL приложения; вложений нет, S3 не участвует.
- Короткий код задачи (как `to:7K3MZ` в референсе) — 5 символов Crockford
  Base32 от UUID, показывается в карточке и ищется строкой поиска.

## Правила домена (из референса, обязательны)

- Статусы и цикл: `inbox → active → done → cancelled → inbox`. Задача с
  незакрытыми зависимостями заблокирована: её цикл `inbox → cancelled`,
  прямой перевод в `active`/`done` отклоняется с причиной «ждёт: …».
- Зависимости не образуют цикла (проверка при добавлении, отказ с
  причиной). Закрытие задачи (`done`) активирует зависимые `inbox`-задачи,
  у которых закрыты все блокеры; `cancelled` блокер считается закрытым.
- Просрочка: срок меньше сегодня и статус не `done`/`cancelled`.
  «Сегодня», «Завтра», «Неделя», «Месяц», «Просрочено» — фильтры по сроку.
- `done` ставит `completedAt`; уход из `done` его снимает. Повторное
  `done` на уже закрытой задаче ничего не делает.
- «Отложить» — срок +1 день и счётчик переносов +1.
- Удаление — мягкое (`deletedAt`), с undo; окончательной очистки нет.
- Undo: последние 5 изменений в памяти процесса, каждое живёт 12 часов,
  сбрасываются при применении изменений извне (зеркало Jira) и при
  перезапуске. Отменяется ровно то изменение, что было сделано; если
  задача с тех пор менялась, шаг недоступен.
- Сортировка: приоритет, статус, срок или дата создания; вторичная — по
  названию. Фильтры и сортировка переживают перезапуск.
- Каждое изменение задачи пишется в журнал версий (кто: пользователь или
  провайдер; когда; что изменилось) — основа для будущей синхронизации
  между устройствами и для undo.

## Как это устроено

### Модули

- `MakoshTasks` — локальный домен, учёт времени, контракты провайдера,
  журнал попыток, хранилище PostgreSQL, QA-изоляция, синтетика.
- `MakoshJira` — перенос из `MacTowerWorkTracking`: транспорт
  (`JiraHTTPSession`, `JiraTransport`), `JiraRESTClient`, разбор
  (`JiraResponseParsing`), переходы (`JiraTaskTransitions`), адаптер Cloud
  (`JiraCloudAdapter`), хранилище токена, диагностика с кодами стадий.
  Адаптер Data Center и OAuth 1.0a не переносятся в этой части, но
  протокол `JiraAdapter` остаётся общим для обоих. Пин —
  `Dependencies/Jira.lock.json` (источник `https://git.sh-inc.ru/avm/mac-tower.git`,
  закоммиченная ревизия `317eeaf`, лицензия MIT, перечень перенесённых
  файлов; незакоммиченные правки локального чекаута не используются);
  уведомление в `THIRD_PARTY_NOTICES.md`. Сборка и тесты не читают
  `mac-tower`. Переносимого меньше, чем звучит: `JiraAPIAdapter` MacTower
  заточен под синхронизацию worklog, а комментарии, смена исполнителя,
  правка полей, статусы проекта и ADF пишутся заново по его образцу;
  `JiraConnection`/`JiraCredentialStore`/`JiraSyncService` зависят от
  `MacTowerCore` и заменяются типами Makosh (`MakoshSecretStore`).
  Первый шаг плана — оба референса в `references.lock.json` и, по правилам
  `AGENTS.md`, в XERJ: `TaskOrchestrator` (исследовательский клон,
  `055c1f1`) и `mac-tower` (локальный чекаут, `317eeaf`).
- Приложение: `Sources/MakoshApp/Tasks` — хост раздела, витрины «Мои» и
  «Jira», карточка задачи, быстрый ввод, таймер в строке состояния,
  Настройки → Задачи; кнопки «Списать время…» и предложение таймера в
  Telemost.

### `MakoshTasks`

- `Task` (локальная запись): `id`, `code`, `title`, `status`, `priority`,
  `list`, `tags`, `due`, `start`, `estimate`, `url`, `postponed`,
  `dependsOn: [UUID]`, `notes`, `source: TaskSource?`, `createdAt`,
  `updatedAt`, `completedAt`, `deletedAt`, `revision`.
- `TaskSource` = `ServiceIdentity` Makosh (сервис `jira`, аккаунт =
  подключение, внешний id = id задачи Jira) плюс `membership`: почему
  задача в «Моих» — `assigned`, `mentioned`, `kept` (пользователь оставил
  после снятия назначения), `none` (видна только в витрине «Jira»).
- `TaskProviderObservation`: снимок задачи провайдера (ключ, проект, тип,
  статус с категорией, приоритет, исполнитель, автор, метки, срок,
  `updated`, описание ADF и текст, комментарии, мои worklog, ссылка),
  `observedAt`, версия; хранится как есть (JSON) и проецируется в поля.
- `TaskTimeEntry`: `id`, `taskID`, `source` (`timer`, `manual`, `meeting`),
  `startedAt`, `seconds`, `note`, `meetingID?`, `jira: TaskJiraAttemptRef?`
  (ссылка на попытку и подтверждённый `worklogID`).
- `TaskTimer`: одна строка (`taskID`, `startedAt`, `note`); остановка
  создаёт `TaskTimeEntryDraft`, подтверждение — запись и, при галочке,
  попытку worklog.
- `TaskJiraAttempt`: `id`, `taskID`, `kind` (`transition`, `worklog`,
  `comment`, `fields`, `assignee`), `payload`, `state` (`queued`, `sent`,
  `unknown`, `confirmed`, `rejected`), `createdAt`, `resolvedAt`,
  `resultID?`, `reason?`. Переходы состояний только через
  `TaskJiraAttemptJournal`; подтверждение worklog после `unknown` —
  перечитать worklog задачи и сопоставить по (`started`, `seconds`,
  автор, примечание); перехода — перечитать статус; комментария —
  перечитать комментарии по автору и тексту; остальных — перечитать поля.
  Совпадение одно — `confirmed`, нет — `rejected` с причиной,
  несколько — остаётся `unknown` с подсказкой.
- `TaskDomain` (чистые правила): `nextCycleStatus`, `isBlocked`,
  `wouldCreateCycle`, `activateDependents`, `overdue`, `postpone`,
  `parseQuickEntry` (с предпросмотром), `parseDate`.
- `TaskStore` (actor, PostgreSQL, схема приложения, не архивная; в
  переносимую резервную копию задачи в этой части не входят — вторая
  очередь): таблицы `tasks`, `task_versions`,
  `task_sources`, `task_source_versions`, `task_time_entries`,
  `task_timer`, `task_jira_attempts`, `task_jira_connections`
  (токен — в `MakoshSecretStore`), `task_preferences` (фильтры,
  сортировка). Любое изменение — транзакция с записью версии; `revision`
  растёт, undo проверяет её.
- `TasksQAIsolation`: одна `qa_tasks_` схема, `--database-config`, фейковый
  `JiraAdapter` в памяти с задачами, переходами, worklog и комментариями.

### `MakoshJira`

- `JiraAdapter` (protocol): `currentUser`, `searchIssues(jql, cursor)`,
  `issue(id, expandTransitions)`, `comments(issueID, cursor)`,
  `worklogs(issueID)`, `transitions(issueID)`, `transition(issueID,
  transitionID, fields)`, `addWorklog`, `addComment`, `updateFields`,
  `assign(issueID, accountID?)`, `assignableUsers(projectKey, query)`.
  `JiraCloudAdapter` реализует его; `JiraAdapterError` с кодами без тела
  ответа.
- `JiraMirror` (actor в `MakoshTasks`, пользуется адаптером): JQL зеркала
  `(assignee = currentUser() OR comment ~ "<accountId>") AND updated >=
  "<окно>" ORDER BY updated ASC`; страницы по `nextPageToken`; недействительный
  курсор — один сброс страницы, как в MacTower. Результат применяется в
  `TaskStore` как наблюдение: новая задача — локальная запись `inbox` с
  `membership`; изменённая — новая версия наблюдения; ушедшая из выборки
  (переназначена не из Makosh) — `kept`, если есть локальная активность
  (локальный статус `active`, идущий таймер, запись времени без
  отправленного worklog, попытка в `queued`/`sent`/`unknown`), иначе
  `none` с пометкой «перестала быть вашей» в карточке; запись и история
  остаются. Витрина «Jira» показывает `assigned`, `mentioned` и `kept`;
  `none` находятся поиском и несут пометку «не обновляется с …»,
  открытие карточки перечитывает задачу. Проверка категории «Готово» →
  локальный `done` по анти-цели 1.
- Упоминания: если Jira отклоняет `comment ~` с accountId, зеркало
  честно отключает часть «упомянули» для подключения и показывает это в
  Настройках; назначенные задачи продолжают идти. Проверяется на живой
  Jira в QA пользователя.

### Приложение

- Раздел «Задачи» в боковой панели (`Destination.tasks`, символ
  `checklist`). Слева — фильтры «Моих» (Сегодня, Завтра, Неделя, Месяц,
  Просрочено, статусы, списки, теги) и подключения Jira (проекты как
  группы). Середина — список задач или доска Jira; справа — карточка
  задачи. Колонка справа, как у «Файлов» и панели ИИ, не лист.
- Карточка задачи Jira: верх — поля Jira (ключ, статус с кнопками
  доступных переходов, исполнитель с «Передать…», приоритет, срок, метки,
  описание, комментарии с полем ответа, мои worklog); низ — локальный слой
  и время. Отправки показывают состояние попытки (Отправляется → Принято /
  Отклонено: причина / Неизвестно: Проверить · Отказаться).
- Таймер: кнопка «▶» у задачи; в строке состояния раздела — идущий таймер
  с названием, временем и «■». Остановка — черновик (задача, дата, начало,
  длительность с правкой, примечание, «Отправить в Jira» для задач Jira).
- Telemost: «Списать время…» в карточке встречи; предложение таймера при
  «Открыть встречу» через `TasksHost` в окружении, без импорта типов
  Telemost в `MakoshTasks` (передаются `localTitle`, `notes` и id встречи).
- Настройки → Задачи: подключения Jira (добавить, проверить — `myself`,
  убрать), период опроса, «Искать упоминания», «Предлагать worklog для
  задач Jira» (по умолчанию включено).
- Доступ и приватность: раздел не читает чаты и письма; упоминания
  приходят только из Jira. Задачи не попадают в индекс ИИ.

### Данные и журналы

- Версии задач и наблюдений — append-only; удаление мягкое. Удаление
  подключения Jira оставляет задачи с `membership` `none` и пометкой
  «подключение удалено»; токен удаляется из Keychain первым.
- Попытки Jira переживают перезапуск: `sent` без ответа при старте
  становится `unknown`. Параллельные попытки одного вида по одной задаче не
  допускаются (вторая ждёт).
- Изменения зеркала применяются только после проверки, что подключение и
  поколение контекста те же (как у остальных сервисов).

## Что остаётся строителю

- Точная форма JQL окна и размер страницы; формат текстовой проекции ADF.
- Разметка доски «Jira»: по статусам или по категориям, когда статусов
  много; порядок колонок.
- Как показывать заблокированные задачи и причину блокировки в списке.
- Схема таблиц PostgreSQL и индексы; формат `code`.
- Сопоставление ключа Jira в названии встречи: регулярное выражение из
  MacTower (`(?<![A-Z0-9])[A-Z][A-Z0-9_]{1,19}-[1-9][0-9]{0,9}(?![0-9])`)
  переносится как есть.
- Содержимое синтетической Jira для QA.

## Мои решения (не пользователя)

- Задача Jira при первом появлении получает локальный статус `inbox` и
  приоритет 4, без переноса приоритета Jira в локальный.
- Локальный `done` по категории «Готово» Jira — единственный автоматизм;
  обратного нет.
- Один таймер на приложение; запуск второго предлагает остановить первый
  с черновиком.
- Worklog в Jira — по галочке в черновике, по умолчанию включённой для
  задач Jira; локальная запись хранится в любом случае.
- Переданная коллеге задача остаётся в «Моих» со статусом `membership`
  `kept` до явного «Убрать из моих»; упомянутые задачи приходят в `inbox`
  с пометкой «вас упомянули» и не меняют своего статуса, пока
  пользователь их не возьмёт.
- Персоны референса заменяются позже ссылкой на контакт Makosh; в этой
  части их нет.
- Ответы на вопросы свежего читателя: описание Jira правится только в
  простом ADF; запись времени с подтверждённым worklog закрыта для правки
  и удаления; ушедшая из выборки задача остаётся `kept` при локальной
  активности; список эндпоинтов открыт; оба референса идут в
  `references.lock.json`, пин Jira указывает на приватный Gitea
  пользователя; таблицы задач — в схеме приложения без резервной копии в
  этой части; worklog короче минуты не отправляется (Jira требует ≥ 60 с),
  черновик округляет вверх до минуты.

## Проверка

- Юнит: правила домена (цикл, блокировка, активация, просрочка, undo),
  быстрый ввод и даты, журнал попыток (все переходы состояний,
  сопоставление после `unknown`), применение наблюдений зеркала
  (новая, изменённая, ушедшая, «Готово» → `done`, `kept`), таймер через
  перезапуск, черновик записи, адаптер Cloud на фикстурах ответов (включая
  429, `Retry-After`, недействительный курсор), ADF туда и обратно.
- Интеграционные: `TaskStore` на реальном PostgreSQL в `qa_tasks_`.
- Синтетическая витрина: `scripts/run-tasks-qa.py`, осмотр обеих витрин,
  пяти действий и таймера.
- Живая проверка — только по команде пользователя, на выбранном им
  подключении и задаче; первый worklog — одна минута на тестовую задачу.

## Вторая очередь (не в этой части)

Планер дня с записью времени из слотов; повторы (RRULE, порождение
следующего экземпляра детерминированным id, откат); именованные цепочки с
прогрессом; персоны → контакты; уведомления о назначениях и упоминаниях;
карточка «задача» для ИИ; Data Center (PAT, OAuth 1.0a из MacTower);
ставки, сводки по месяцам, счета и оплаты; синхронизация между
устройствами по журналу версий.
